# 분할 영상 다운로드 속도 개선

## 운영에서 확인한 지연

2026-09-30, 릴리스 `2adfbd66a874d6ca68371252698717c67239cd3d`의 작업
`d898ddde2bb14ea2aa7376ee014f6627`은 저장까지 성공했다. 서버 로그 기준 정보 조회는
4.537초, 다운로드는 451.018초였고, worker가 작업을 받은 시점부터 완료까지 약 507초였다.
다운로드 중 502나 세션 재시도는 관측되지 않았다. 받은 영상 트랙은 720p H.264,
측정 길이는 771초였다. 오디오 전송 중 측정한 처리량은 약 33 KiB/s였다.

기존 코드는 영상과 오디오의 HLS/DASH 조각을 하나씩 받으며 매 요청마다 연결을 만든다.
개별 요청의 대기 시간이 누적되는 구조는 코드로 확인했다. 운영의 451초 중 연결 대기와
실제 회선 대역폭이 각각 얼마를 차지했는지는 아직 분리 측정하지 않았다.

## 변경

- 프록시를 사용하는 분할 다운로드에만 최대 4개 동시 요청을 적용한다. 영상과 오디오
  트랙 자체는 여전히 순서대로 처리하여 전체 동시 요청 수가 4를 넘지 않는다.
- 완료 순서와 관계없이 manifest 순서로 파일을 합친다. HLS 초기화 조각도 첫 위치를 유지한다.
- 메모리에 영상을 모두 올리지 않는다. 최대 4개 조각만 미리 받고, 합친 조각 파일은 즉시 지운다.
  조각 복사 중 임시 중복과 최종 MP4를 포함해 기존 임시 디스크 상한을 유지한다.
- 모든 연결은 같은 프록시 세션과 전체 작업의 시간·바이트·요청 예산을 공유한다.
  카운터와 재시도 결정은 잠금으로 보호한다. 다운로드 복사는 네트워크 사용량에 이중 집계하지 않는다.
- 하나가 실패하면 나머지는 기존 소켓·읽기 제한과 공유 취소 상태를 통해 종료한다.
  모든 스레드가 종료된 뒤 파일을 정리하고 기존의 최대 1회 세션 재시도 정책을 적용한다.
  인증·접근 거부·요청 제한 응답은 세션 재시도 대상이 아니다.
- 파일 트랙별 `source_transfer` 로그에 조각 수, 동시 요청 수, 다운로드 바이트와 시간을 남긴다.
  원본 주소와 프록시 인증정보는 기록하지 않는다.
- 프록시 없는 다운로드와 단일 파일 다운로드는 기존 순차 경로를 유지한다.

## 검증 범위

로컬 모의 전송 비교: 24개 조각, 각 요청에 25ms 지연, 동일 파일/바이트/요청 수.
두 실행에서 약 3.17배와 3.73배의 속도 차이를 측정했다. 순서·해시·요청 수·바이트 수는
동일했다. 실행 환경 영향을 받는 시간 비율은 CI 성공 조건으로 사용하지 않고,
동시성 상한·순서·전체 사용량·종료를 결정적으로 검증한다.

테스트는 순서 뒤바뀜, 느린 첫 조각의 prefetch 상한, 바이트·wire·요청·시간 제한,
취소 시 스레드 종료, 재시도 한도, HLS 초기화 조각 순서, 실제 FFmpeg와
API → worker → 보관함 → 미리보기·테넌트 격리를 포함한다.

이 수치는 DataImpulse/YouTube 실측 개선율이 아니다. 이번 로컬 시험에는 외부 프록시
트래픽을 사용하지 않았다. 운영 적용 후 같은 영상의 `source_transfer`와
`source_import_stage`를 비교해야 실제 개선 폭을 판단할 수 있다.
